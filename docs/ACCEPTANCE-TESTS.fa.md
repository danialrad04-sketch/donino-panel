# قرارداد آزمون پذیرش Donino 1.0

نسخه سند: ۱ — ۲۰۲۶-۱۰-۱۵. این سند **طرح آزمون آینده** است. وجود شناسه یا تیک در شرح سناریو، به معنی اجرا یا عبور نیست. نتایج واقعی نسخهٔ ۰.۲ در [VALIDATION](VALIDATION.md) ثبت شده‌اند؛ CI فعلی آزمون‌های v0.2 را اجرا می‌کند و هنوز این مجموعهٔ هدف را پیاده نکرده است.

## سطوح مدرک و محیط

| سطح | محیط | چه چیزی را اثبات می‌کند؟ |
|---|---|---|
| D — سند | بررسی پیوند، ماتریس و شناسه‌ها | انسجام برنامه؛ نه کارکرد سرویس |
| L — محلی | fixture، موتور واقعی loopback، DB موقت | قرارداد و اجرای کنترل‌شده؛ نه دسترسی اینترنت یا همه کلاینت‌ها |
| V — VM | سیستم‌عامل تمیز و سرویس واقعی | نصب، پورت، firewall، reboot، migration و failure recovery |
| E — خارجی | VPS/دامنه واقعی و کلاینت نسخه‌دار | صدور/تمدید TLS و اتصال واقعی در شبکه هدف |
| G — شبکه بازی | ISP/دستگاه/سرویس معلوم | فقط همان سناریوی login/download/gameplay و مسیر اندازه‌گیری‌شده |

هدف اولیه VM: Ubuntu 24.04 و Debian 12 روی amd64؛ arm64 پیش از ادعای پشتیبانی، شاهد مستقل می‌خواهد. DB: SQLite شخصی و PostgreSQL حرفه‌ای. زمان UTC، نسخه OS/core/client، checksum باینری، منابع ماشین و نرخ/بار آزمون در مدرک ثبت شوند. داده آزمایشی و credential موقت استفاده شوند؛ artifact عمومی نباید رمز، توکن، کلید خصوصی، IP مشتری یا backup واقعی داشته باشد.

## حدهای اولیه هدف

این عددها SLO طراحی هستند و برای نسخهٔ ۰.۲ ادعای جدید نمی‌سازند. تغییرشان نیازمند اصلاح این سند و نتیجه آزمون است.

- نمونه‌برداری مصرف هدف حداکثر ۵ ثانیه در شرایط بار اعلام‌شده؛ مهلت اعمال محلی قطع حداکثر ۱۰ ثانیه. انقضا با ساعتِ دارای حداکثر خطای ۲ ثانیه آزموده شود؛ در ساعت ناسالم، نود نباید lease تازه را بی‌بررسی تمدید کند.
- TTL اولیه budget lease حداکثر ۶۰ ثانیه است؛ در قطع شبکه و بدون تمدید، سرویس حفاظت‌شده حداکثر تا deadline محلی lease + ۱۰ ثانیه + خطای ساعت بسته شود. برای پیکربندی عددی دیگر، همان حد در مدرک آزمون ثبت شود. TTL قبلی عامل v0.2 همچنان ۱۲۰ ثانیه پیش‌فرض است.
- گزارش تکراری/خارج از ترتیب نباید حتی یک بایت دوباره شارژ کند. خطای ناشی از crash برای بایت نمونه‌برداری‌نشده جدا اندازه‌گیری شود؛ تحمل خطای crash با dedup اشتباه نشود.
- حد اضافه‌مصرف فقط با نرخ حداکثر معلوم در هر نود قابل ادعاست: مجموع بودجه تخصیص‌یافته از مانده بیشتر نشود؛ پنجره نمونه‌برداری/اعمال/ساعت و نرخ محدودشده مبنای bound است. بدون نرخ محدود، ادعای قطع در بایت دقیق رد می‌شود.
- ظرفیت CPU/RAM/کاربر/throughput و RPO/RTO هنوز عدد اثبات‌شده ندارند. فاز ۱۴ باید profile سخت‌افزار و بار، p50/p95/p99 و اهداف عددی را پیش از آزمون نهایی ثبت کند؛ نتیجهٔ بدون workload معلوم، تأیید ظرفیت نیست.

## مبنای موجود و شکاف آزمون

۳۴ آزمون فعلی API/عامل/دفتر مصرف/migration/Xray و smoke مرورگر در [گزارش ۰.۲](VALIDATION.md) وجود دارند. مثال‌های قابل بازاجرا: `tests/test_xray.py` برای سه پروتکل و انتقال واقعی، `tests/test_journal.py` برای replay، `tests/test_migrations.py` برای schema و `tests/browser_smoke.py` برای رابط/پورتال. این‌ها بخشی از DATA/USAGE/PROTO/UI را پوشش می‌دهند، اما گواه PostgreSQL، mTLS، بودجه اجاره‌ای، SSL خارجی، DNS یا موتورهای جدید نیستند.

تست واحد برای منطق و failure path مفید است؛ هر قابلیت شبکه علاوه بر آن تست موتور و کلاینت واقعی لازم دارد. پس از تغییر صرفاً مستند، بررسی DOC کافی است؛ CI موجود می‌تواند regression محصول را هم اجرا کند. تست‌های آینده فقط با پیاده‌سازی همان قابلیت به CI اضافه می‌شوند.

## قالب مدرک پذیرش

هر اجرای واقعی یک رکورد با این فیلدها تولید می‌کند؛ نمونه زیر عمداً اجراشده نیست:

```json
{
  "test_id": "PROTO-01",
  "feature_ids": ["F-16"],
  "protocol_id": "P-10",
  "status": "not-run",
  "commit": null,
  "environment": null,
  "engine_version": null,
  "engine_asset_sha256": null,
  "client_version": null,
  "workload_and_limits": null,
  "started_at_utc": null,
  "expected": "real transfer, accounting and revocation",
  "observed": null,
  "redacted_artifacts": [],
  "limitations": [],
  "reviewer": null
}
```

رکورد واقعی باید SHA دقیق، محیط، شرایط شبکه و شاهد redacted داشته باشد. برای `pass`، همه مراحل اجباری همان سناریو لازم است؛ `partial` یا `not-run` در ماتریس به پشتیبانی پایدار تبدیل نمی‌شود. پیش از انتشار، مدارک به SHA انتشار مرتبط شوند؛ تغییر موتور/config/حسابداری پس از تست، اجرای دوباره موارد تحت تأثیر را لازم می‌کند.
