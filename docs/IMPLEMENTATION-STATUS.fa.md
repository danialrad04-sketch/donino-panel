# اجرای برنامهٔ Donino 1.0

این پرونده وضعیت واقعی اجرا را ثبت می‌کند. مجوز کاربر برای پیشبرد تمام فازها تا انتشار ۱.۰ برقرار است؛ برای کارهای عادی توسعه، آزمون و ثبت در GitHub تأیید دوباره لازم نیست. اولویت با وابستگی‌های [برنامهٔ جامع](MASTER-PLAN.fa.md) است.

## زیرساخت در دسترس

کاربر اعلام کرده فعلاً فقط محیط آزمایشی فعلی در دسترس است. PostgreSQL واقعی در کانتینر محلی، Xray واقعی و Chromium در همین محیط قابل آزمون‌اند. دامنه عمومی، VPS خارجی، کنسول و شبکه ISP واقعی در اختیار این مرحله نیستند؛ صدور عمومی ACME یا آزمون بازی/شبکه خارجی تأییدشده اعلام نخواهند شد. ساخت و آزمون مستقل این امکانات ادامه می‌یابد.

| ۰ | انجام‌شده | شش سند و منابع ثابت؛ commit `484b13f` |

## یادداشت عملیاتی زیرساخت داده

- متغیر `DONINO_DATABASE_URL` یک URL از نوع PostgreSQL است؛ در نبود آن، `DONINO_DB` همچنان مسیر SQLite است. pool فعلی PostgreSQL پنج اتصال و حداکثر پنج overflow دارد. این حد پیش‌فرض است و ادعای آزمون ظرفیت نیست.
- مهاجرت قدیمی SQLite به schema 2 حفظ شده است؛ Alembic سپس `0001_foundation` را اعمال می‌کند. نسخهٔ schema پایه در `app/schema_v1.py` ثابت است؛ تغییر بعدی باید revision تازه داشته باشد. برای SQLite موجود پیش از foundation یک backup خصوصی جدا ایجاد می‌شود.
- `python -m app.cli import-sqlite SOURCE` فقط در مقصد خالی مجاز است؛ snapshot منبع را کپی و همان کپی را مهاجرت می‌دهد. شناسه، subscription، کلید قبلی و legacy usage حفظ می‌شوند. منبع اصلی تغییر نمی‌کند.
- `backup DESTINATION` برای SQLite فایل سازگار SQLite و برای PostgreSQL آرشیو منطقی با snapshot تراکنشی repeatable-read می‌سازد. `restore-archive SOURCE` فقط آرشیو همان revision را در مقصد خالی می‌پذیرد؛ restore خراب rollback می‌شود. این پشتیبان DB است، نه backup کامل ماشین.
- seedهای MFA با Fernet و کلید خصوصی `DONINO_KEY_FILE`، پیش‌فرض `master.key` کنار مسیر `DONINO_DB`، رمز می‌شوند. کلید اصلی باید جدا و امن پشتیبان/بازیابی شود؛ DB به‌تنهایی برای بازیابی MFA کافی نیست. MFA فعال، sessionها و API tokenهای قبلی همان حساب را باطل می‌کند. recovery code یک‌بارمصرف است.
- پس از مهاجرت به PostgreSQL، همان `DONINO_KEY_FILE` باید در محیط جدید حفظ شود. URL یا رمز DB در repo قرار نگیرد؛ برای نمونه تنظیمات از placeholder استفاده شود.
- دستگاه‌های جدید برای VLESS/VMess/Trojan secret مستقل دارند. دستگاه legacy برای حفظ پروفایل قبلی همان secret را نگه می‌دارد. API غیرفعال‌کردن/چرخش دستگاه و UI آن موجود است؛ قطع نشست در Xray همچنان با restart نود انجام می‌شود.
- گزارش دارای `period_id` دیررس به دوره قبلی می‌رود؛ عامل ۰.۲ این فیلد را ارسال نمی‌کند و محدودیت قدیمی گزارش دیررس پس از reset را دارد. پذیرش کامل USAGE-03 به عامل دوره‌آگاه فاز ۳ وابسته است.

## بررسی‌های برش اول

آزمون‌های محلی PostgreSQL 16، انتقال SQLite→PostgreSQL، بازیابی PostgreSQL در schema مستقل، گزارش هم‌زمان و آزمون‌های API/عامل/Xray اجرا شدند. مرورگر واقعی ساخت دستگاه، assignment، scoped token، setup MFA و ورود recovery را اجرا کرد؛ خطای JavaScript نداشت. نتیجهٔ نهایی هر checkpoint با SHA و CI در گزارش انتشار همان checkpoint ثبت می‌شود؛ این شواهد به معنی تکمیل فازهای بعد یا پذیرش production نیست.

## برش نصب — alpha 2

[راهنمای اجرایی](INSTALLER-PREVIEW.fa.md) مرجع فرمان‌های قابل استفاده است. هر دو محیط OS جداشده با systemd، Debian 12/PostgreSQL 15 و Ubuntu 24.04/PostgreSQL 16، نصب، تکرار، restart، TLS با CA محلی معتبر، ساخت مالک، backup و بازیابی DB+MFA در نمونهٔ جدا و uninstall با حفظ داده را گذراندند. این محیط‌ها کانتینر با systemd و شبکه جدا هستند، نه VM مستقل یا VPS/دامنه عمومی. مسیر ACME واقعی و کیفیت ISP هنوز پذیرش نشده‌اند.

لایهٔ بستهٔ سورس شامل manifest فایل‌ها، checksum، دانلود از ref نسخه‌دار و رد آرشیو نامعتبر پیش از import کد است. bundle رمزگذاری‌شده کلید MFA را همراه DB نگه می‌دارد؛ کلید بازکردن bundle جداست. import/restore، session و API token مدیریتی قبلی را برای جلوگیری از زنده‌شدن دسترسی لغوشده باطل می‌کند. صورت قبلی این سند دربارهٔ backup جداگانهٔ master.key همچنان برای backup خام DB/UI برقرار است.
