# ارتقا از Donino ۰.۱ به ۰.۲

این نسخهٔ نرم‌افزار است؛ انتشار روی GitHub به‌خودی‌خود سرور شما را ارتقا نمی‌دهد. پیش از اجرا، از مسیرهای واقعی نصب و مالک فایل‌ها مطمئن شوید. نمونه‌های زیر مسیرهای systemd راهنمای نصب را فرض می‌کنند و نیازمند مجوز مدیریتی سرور هستند.

## تغییرات مؤثر بر کارکرد

- پنل: schema به شمارهٔ ۲ می‌رسد، ستون‌های ارسال/دریافت و وضعیت عامل افزوده می‌شوند. حساب‌ها، کلیدهای کاربران، توکن اشتراک، کلیدهای REALITY و مصرف قبلی حفظ می‌شوند.
- نود: هنگام آغاز، شناسهٔ نود را از پنل ۰.۲ دریافت می‌کند. بنابراین **ابتدا پنل و سپس نودها را ارتقا دهید**. پنل ۰.۲ heartbeat عامل ۰.۱ را همچنان می‌پذیرد، اما عامل جدید به پنل قدیمی متصل نمی‌شود.
- افزودن صرفِ کاربر روی اتصال‌های موجود، زنده انجام می‌شود. ابطال دسترسی، انقضا، اتمام حجم، تعویض کلید، تغییر پروتکل/پورت و تنظیمات انتقال همچنان باعث restart Xray و قطع نشست‌های جاری می‌شوند.
- اگر تنظیمات جدید پس از اعتبارسنجی در startup شکست بخورند، عامل تلاش می‌کند تنظیمات قبلیِ در حال اجرا را دوباره بالا بیاورد. این بازیابی، تضمین کارکرد در هر خطای سیستم یا سابقهٔ تنظیمات بین rebootها نیست.

## ۱. ثبت نسخه و پشتیبان

پیش از تعویض کد، SHA نسخهٔ فعلی را نگه دارید و با CLI همان نسخه پشتیبان بگیرید:

```bash
cd /opt/donino-panel
git rev-parse HEAD
sudo -u donino env DONINO_DB=/var/lib/donino-panel/donino.db .venv/bin/python -m app.cli backup /var/lib/donino-panel/before-0.2.db
```

نام فایل پشتیبان باید جدید باشد؛ CLI فایل موجود را بازنویسی نمی‌کند. نسخهٔ رمزگذاری‌شده‌ای از پایگاه داده، `/etc/donino/`، فایل‌های TLS و state هر نود را خارج از سرور حفظ کنید. برای یک ارتقای منظم، ابتدا عامل هر نود را در حالی که پنل قدیمی هنوز فعال است متوقف کنید تا آخرین گزارش ارسال شود:

```bash
sudo systemctl stop donino-node
```

این مرحله اتصال‌های همان نود را قطع می‌کند؛ پنجرهٔ نگهداری در نظر بگیرید. سپس سرویس پنل را متوقف کنید.

## ۲. ارتقای پنل

در clone موجود و بدون تغییرات محلی، نسخهٔ ۰.۲ را دریافت و انتخاب کنید. فایل `.env` یا مسیر داده را جایگزین نکنید:

```bash
cd /opt/donino-panel
git fetch origin --tags
git switch --detach v0.2.0
sudo .venv/bin/pip install -r requirements.txt
sudo -u donino env DONINO_DB=/var/lib/donino-panel/donino.db .venv/bin/python -m app.cli migrate
sudo systemctl start donino-panel
```

پیش از فرمان‌های بالا، روی سرور پنل `sudo systemctl stop donino-panel` را اجرا کنید. `migrate` پیش از هر ALTER، پشتیبان سازگار را کنار فایل اصلی با نام `donino.db.pre-v2-XXXXXXXXXXXX.db` و دسترسی `600` می‌سازد. اگر ساخت پشتیبان شکست بخورد، migration ادامه نمی‌یابد. عملیات schema و ثبت شمارهٔ نسخه در یک transaction هستند. پایگاه دادهٔ جدیدتر یا ساختار ناشناخته پذیرفته نمی‌شود. در startupهای بعدی پشتیبان migration تکراری ساخته نمی‌شود.

آدرس `/healthz` باید نسخهٔ `0.2.0` را گزارش دهد. وارد پنل شوید و تعداد کاربران، حجم‌ها و اتصال‌ها را بررسی کنید. مصرف قدیمی در `legacy_used` حفظ می‌شود؛ چون نسخهٔ ۰.۱ فقط مجموع را داشت، نسبت ارسال/دریافت آن قابل بازسازی نیست.

## ۳. ارتقای هر نود

در حالی که سرویس نود متوقف است، همان tag و وابستگی‌ها را روی سرور آن نود نیز دریافت کنید:

```bash
cd /opt/donino-panel
git fetch origin --tags
git switch --detach v0.2.0
sudo .venv/bin/pip install -r requirements.txt
sudo systemctl start donino-node
sudo journalctl -u donino-node -n 50 --no-pager
```

`DONINO_NODE_TOKEN`، `DONINO_NODE_STATE` و نشانی پنل را حفظ کنید. عامل جدید فایل `usage.db` را در state می‌سازد و برای همان شناسهٔ نود و origin پنل ثبت می‌کند. تغییر توکن همان نود مجاز است؛ تغییر شناسه یا origin برای state موجود رد می‌شود. برای انتقال دامنه یا جابه‌جایی state باید گزارش‌های معوق با هویت قبلی تسویه و مسیر قبلی آرشیو شود؛ فایل مصرف را بی‌دلیل حذف نکنید.

عامل جدید و Xray را با systemd مدیریت کنید؛ سرویس پیش‌فرض تمام گروه فرایند را مدیریت می‌کند. قفل state فقط مانع اجرای هم‌زمان دو عامل روی **همان مسیر** می‌شود؛ دو مسیر متفاوت مجوز اجرای دو هسته روی یک پورت نمی‌دهند.

## ۴. تأیید پس از ارتقا

در صفحهٔ نودها، نسخهٔ عامل باید `0.2.0` و هسته متصل باشد. افزودن کاربر روی همان inboundها پس از همگام‌سازی باید روش اعمال «به‌روزرسانی زنده» نشان دهد. ابطال یا تغییر پورت به «اجرای کامل» منتهی می‌شود. اگر rollback رخ داد، روش اعمال «بازیابی تنظیمات» و خطا گزارش می‌شود؛ revision جدید موفق اعلام نمی‌شود. همان revision خراب با فاصلهٔ حداقل ۳۰ ثانیه امتحان می‌شود. پس از مهلت قطع ارتباط/همگام‌سازی، هسته متوقف می‌شود؛ رفع خطا ضروری است.

از بخش اشتراک، صفحهٔ کاربر و QR را روی موبایل امتحان کنید. این صفحه ورود مدیریتی لازم ندارد و خودِ لینک مجوز مشاهده است؛ آن را عمومی نکنید. تعویض لینک اشتراک، لینک قدیمی صفحهٔ کاربر و QR را هم باطل می‌کند.

## بازگشت به نسخهٔ قبل

پیش از بازگرداندن کد، نودها و پنل را متوقف کنید. پایگاه فعلی، پشتیبان‌های migration و صف نودها را آرشیو کنید. باینری/کد قبلی را همراه پشتیبان **پیش از ارتقا** بازگردانید و مالک `donino` و مجوز `600` فایل پایگاه را حفظ کنید. صرفاً downgrade کردن کد روی پایگاه جدید، مسیر بازیابی تأییدشده نیست. سپس نسخهٔ قبلی پنل و عامل را بالا بیاورید. تغییرات و مصرف ثبت‌شده پس از زمان پشتیبان در پایگاه بازگردانی‌شده وجود ندارند؛ بازیابی داده و شمارنده‌ها باید با این فاصلهٔ زمانی هماهنگ شود.
