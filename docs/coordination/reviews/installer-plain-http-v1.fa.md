# بازبینی تغییر نصب HTTP کلاد — PR۲۷

مبنای بازبینی: `claude/installer-plain-http`، head
`1d024687978d09498b4a18dc961ca9c5679e58bd`، روی main پس از OpenVPN alpha15.
کاربر خواست تغییر تازهٔ کلاد بررسی شود؛ این تغییر با مأموریت قدیمی Mihomo
در checkpoint کلاد یکی نیست. فایل checkpoint قدیمی او تغییر نکرده است.

## تصمیم فعلی

هنوز برای ادغام آماده نیست. پیکربندی سادهٔ NGINX و parse شدن flag، شاهد
کامل نصب، repair و upgrade حالت تازه نیستند. Shadowsocks در PR۲۶ مستقل
ادامه دارد؛ حالت HTTP این شاخه وارد انتشار alpha16 نمی‌شود.

## یافته‌های بازتولیدشده

۱. **repair حالت HTTP همیشه به گواهی نیاز پیدا می‌کند** —
`ops/install.py:850` در head بالا بدون توجه به `tls_mode=none` تابع
`validate_certificate` را صدا می‌زند و خط بعدی proxy را با `tls=True`
می‌سازد. نصب سالم HTTP اصلاً آن دو فایل را ندارد؛ repair با
`Certificate and private key files are required` متوقف می‌شود. بازتولید:
state خصوصی آزمایش با domain وtls_mode=none، symlink current معتبر و مسیر
config خالی؛ فراخوانی واقعی repair با `--tls none`، بدون اجرای هیچ فرمان
میزبان، به همان خطا رسید. باید repair بر اساس حالت ذخیره‌شده رفتار کند؛
خاموش‌کردن اعتبارسنجی گواهی برای حالت‌های HTTPS راه‌حل نیست.

۲. **ارتقای نصب HTTPS قدیمی با گواهی موجود اشتباهاً رد می‌شود** —
در guard جدید `install`، stateهای پیش از این تغییر که `tls_mode` ندارند
به‌عنوان `acme` فرض شده‌اند. نصب قدیمی با `--tls existing` معتبر است ولی
تکرار همان فرمان اکنون خطای `TLS mode cannot change` می‌دهد. بازتولید با
state شامل domain و بدون tls_mode و فراخوانی install با `--tls existing`
و مسیرهای گواهی آزمایش، پیش از نصب بسته/تغییر سرویس به همین خطا رسید.
نبود metadata جدید نباید معادل شاهد قطعی استفاده از ACME دانسته شود؛
مرز HTTP/HTTPS و سازگاری نصب‌های قبلی باید جدا اعتبارسنجی شوند.

۳. **محدودهٔ ارتباط نود روشن نیست** — HTTP بدون client certificate جای
کنترل‌پلن HTTPS/mTLS را نمی‌گیرد. agent.enroll و origin validation نباید
برای کارکرد این flag تضعیف شوند. راهنمای این حالت باید صریح بگوید ثبت امن
و اتصال نود دوردست نیازمند کنترل‌پلن HTTPS است؛ ادعای نصب کامل چندنودی روی
HTTP ساده تأیید نشده است. این مورد محدودیت طراحی/مستندات است، نه شاهد جعل
هویت در پراکسی فعلی.

## مسیر تکمیل

repair/upgrade حالت HTTP و سازگاری state قدیمی با آزمون رفتاری پوشش داده
شوند؛ نصب، ورود/bootstrap، cookies، نصب مجدد، repair، حفظ DB/کلید و uninstall
روی Debian12 وUbuntu24 ایزوله بررسی شوند. خطاهای DNS/Smart DNS و تغییر حالت
TLS باید پیش از تغییر میزبان رخ دهند. سپس بر پایه main شامل alpha16،
manifest تازه وCI head دقیق لازم است. آزمایش VPS/صدور عمومی ACME همچنان
انجام نشده است؛ مجوز انتشار HTTP عمومی از این بازبینی استنباط نمی‌شود.

شواهد محلی بازبینی فقط state وگواهی آزمایشگاهی بودند؛ کلید/توکن/پایگاه دادهٔ
کاربر خوانده یا منتشر نشد و دستور شبکه/سرویس میزبان اجرا نشد.

## ادامهٔ پیاده‌سازی — alpha17

به درخواست تازهٔ کاربر، patch اصلی HTTP در شاخهٔ `development/installer-menu`
روی main شامل alpha16 منتقل و دو ایراد بالا اصلاح شدند. repair بدون گواهی،
سازگاری provider نصب HTTPS قدیمی، HTTP با IPv4 بدون دامنه، نگهداری CA خصوصی
و منوی TTY مستقل اضافه شدند. پذیرش واقعی HTTP/reinstall/repair/حفظ کلید و
launcher در دوOS آزمایشگاهی موفق شد. این نتیجه تأیید head قدیمی PR27 نیست؛
تحویل اصلاح‌شده در PR جدا و با CI head نهایی انجام می‌شود.
