# کار فعال Codex به دستور کاربر

کلاد به دلیل لیمیت فعلاً متوقف است. مأموریت تازه برای او تعیین نمی‌شود؛ Codex تحویل نیمه‌تمام Mihomo و ادامهٔ پنل را انجام می‌دهد. checkpoint قبلی کلاد در history بدون تغییر نگهداری می‌شود. ادامهٔ کلاد فقط پس از دستور بعدی کاربر و انتساب تازه است.

گام ۱: تحویل PR ۱۷ را کامل کن؛ SNI خروجی Trojan برای Mihomo باید صحیح باشد. هر شش مسیر TLS باید با خروجی واقعی subscription انتقال موفق، رد CA/hostname اشتباه، حسابداری دستگاه و ابطال داشته باشند. expected failure و بازنویسی اصلاحیِ proxy در fixture نباید جای رفع عیب محصول را بگیرد. مستندات، CI پین‌شده و وضعیت تحویل را با نتیجهٔ واقعی هماهنگ کن.

گام ۲: یکپارچگی تانل را با binding پایدار plan به node/inbound موجود، ساخت پورت مقصد از DB، revision guard و وضعیت قابل پیگیری جلو ببر. موفقیت نصب حامل یا اتصال TCP را تأیید انتقال VPN یا مجوز انتشار خودکار endpoint ننام. مرحلهٔ انتشار اشتراک باید پس از پذیرش واقعی و با حفاظت در برابر تغییر تنظیمات باشد.

کار در شاخه‌های محدود و آزموده، manifest و PR/ادغام با بررسی دقیق head ادامه دارد. نسخه فقط در صورت بستهٔ محصول قابل انتشار تغییر کند. VPS/دامنهٔ واقعی کاربر وجود ندارد؛ آزمایش local/CI و محدودیت‌هایش صریح ثبت شود. مسیر schema فعلی main حفظ شود و migration با backup و تست SQLite/PostgreSQL انجام گیرد.

گام ۳، درخواست تازهٔ کاربر: Smart DNS واقعی برای دامنه‌های منتخب، خروجی‌های اصلی/جایگزین و تغییر نود، سهمیهٔ مستقل و نصب قابل استفاده را روی main پس از PR ۱۹ پیاده کن. خروجی تولید بدون TLS verification، DIRECT fallback، اشتباه‌گرفتن بایت DNS با بازی، فعال‌کردن بی‌اجازهٔ واردات یا ادعای v1 کامل مجاز نیست. schema 13 با backup/restore محافظت‌شده، پذیرش واقعی شبکه، رابط فارسی و نصب اختیاری بررسی شود. نتیجه در PR و prerelease alpha.11 ثبت شود؛ کلاد همچنان متوقف است.

گام ۴: نصب مستقل نقش Smart DNS exit، گواهی و تمدید امن، credential خصوصی پایدار، سرویس محدود systemd، health واقعی TLS/auth، نصب مجدد و حذف با حفظ داده را تکمیل کن. خروجی نیازمند کنترل‌پنل/DB اضافی نیست و firewall/routes میزبان را تغییر نمی‌دهد. پذیرش دو OS ایزوله با گواهی محلی لازم است؛ ACME عمومی و بازی/WAN هنوز ادعا نشوند. ادامهٔ فاز WireGuard/OpenVPN طبق طرح باقی است.

گام ۵، درخواست تازهٔ کاربر: تانل ایران/خارج را با پایش اختیاری و کلاینت واقعی، تمدید محدود endpoint، حذف انتشار هنگام خرابی و بازیابی فقط در محدودهٔ رضایت اولیه تکمیل کن. لغو دستی، تغییر job/source/device/دوره و restore باید اجرای دیررس را fence کند. heartbeat و نصب سرویس محدود، آزمون واقعی قطع/بازیابی حامل و عدم ادعای WAN لازم‌اند. schema 14 با backup پیش از migration و restore محافظت شود.

گام ۶: به درخواست ادامهٔ همهٔ فازها برای stable v1، WireGuard را با کلید مستقل دستگاه، IP/peer، خروجی conf/QR، پیکربندی امضاشده، دفتر پایدار مصرف و حذف واقعی peer در quota/expiry/revoke پیاده کن. مرز Xray و دوره‌های مصرف حفظ شود؛ lease quota بدون supervisor مربوط رد شود. آزمون کلاینت/شبکه واقعی ایزوله لازم است؛ نصب/forwarding/NAT و محدودیت‌ها صریح ثبت شوند. سپس OpenVPN و gateهای باقی‌مانده طبق طرح ادامه دارند.

گام ۷، درخواست تازهٔ کاربر: فعلاً تکمیل پروتکل‌ها اولویت دارد. OpenVPN UDP/TCP با CA و گواهی مستقل دستگاه، خروجی ovpn، intent امضاشده و عامل نشست با دفتر پایدار مصرف/دوره/حجم/انقضا/ابطال و کلاینت واقعی پیاده شود. طراحی نود چندلوکیشن، enrollment امن و مسیرهای انتخابی سرویس/دامنه و UDP بازی باید ادامه یابد؛ DNS صرفاً با پاسخ آدرس، تضمین عبور UDP بازی نیست. نصب/شبکهٔ میزبان بدون مجوز عملیاتی تغییر نکند و برابری کامل با PasarGuard/3x-ui ادعا نشود.

گام ۸: پس از تحویل alpha15، Shadowsocks با روش‌های رمز معتبر و credential مستقل دستگاه، URI استاندارد و Mihomo، حسابداری/دوره و قطع نشست واقعی روی Xray منتخب پیاده شود. 2022 فقط با قرارداد multi-user اثبات‌شده پذیرفته شود؛ روش ناامن none یا fallback بدون رمز عرضه نشود.

گام ۹: به درخواست تازه کاربر، نصب بدون SSL، منوی مستقل تمام‌صفحه ترمینال، setup خودکار پیش‌نیازها و مسیر دامنه/ACME/تمدید حرفه‌ای تکمیل شوند. از معماری 3x-ui وPasarGuard تحقیق شود؛ کد اختصاصی با حفظ manifest، نصب مجدد و داده/کلید و قرارداد HTTPS/mTLS نودها. HTTP شامل IP بدون دامنه و repair باشد؛ آزمون دوOS ایزوله لازم است؛ صدور عمومی ACME بدون VPS ادعا نشود.

گام ۱۰: به درخواست کاربر، رابط گوشی با سلسله‌مراتب روشن، منوی همبرگری دسته‌بندی‌شده، نوار پایین محدود به مقصدهای اصلی، حفظ دسترسی نقش‌ها، فرم و جدول خوانا و هدف لمس مناسب اصلاح شود. focus/Escape/پس‌زمینه و safe-area/چرخش صفحه و تغییر اندازه در مرورگر واقعی بررسی شوند؛ دسترسی API یا پروتکل‌ها تغییر نکنند.

گام ۱۱: به درخواست کاربر، DNS معمولی با IP سرور و UDP/TCP بدون DoH/دامنه/SSL پنل قابل نصب و استفاده شود؛ مدیریت IP مشتری، quota/expiry و راهنمای واقعی رابط/پرتال تکمیل شوند. معماری doctor-dns مطالعه شود؛ IP عمومی به‌تنهایی تضمین عبور UDP بازی نیست. TLS و احراز هویت خروجی‌های موجود ضعیف نشوند؛ نصب ایزوله و ترافیک واقعی DNS لازم است.
