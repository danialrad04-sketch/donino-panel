# تانل خودکار Donino Panel — نقشه‌های متصل به پنل در alpha 9

این نسخه، عملیات تایپ‌شدهٔ Donino Tunnel را از صفحهٔ «تانل خودکار» همین پنل در دسترس مالک می‌گذارد: جفت‌سازی HTTPS پین‌شده، آزمون کانال مدیریت، پیش‌نمایش نقشه و پورت‌ها، شروع نصب دوطرفه و پیگیری job پایدار. **نصب اولیهٔ نقش‌ها خودکار از داخل Donino Panel انجام نمی‌شود.** پس از آماده‌سازی نقش ایران و خارج، نصب حامل‌ها با worker موجود انجام می‌شود. VPS یا دامنهٔ واقعی کاربر در این مرحله فراهم نشده است.

## نقشهٔ متصل به ورودی پنل

در alpha 9، حالت پیش‌فرض فرم «از اتصال‌های همین پنل» است. نود خارج و ورودی‌های فعال آن را انتخاب و پورت عمومی ایران را تعیین کن؛ target از پورت ثبت‌شدهٔ inbound ساخته می‌شود و فقط loopback روی همان خارج است. **انتخاب نود باید با سرور خارج جفت‌شده مطابقت داشته باشد**؛ تطابق دامنه و IP به معنی اثبات هویت یک میزبان نیست و این مرحله مالکیت سرور را از روی DNS حدس نمی‌زند. حالت قدیمی پورت دستی جداگانه باقی است.

نقشه و انتخاب ورودی‌ها در جدول `tunnel_bindings`، schema 11، پایدار می‌مانند. فهرست روی صفحه پس از بارگذاری دوباره هم باقی است؛ «مرور نقشه» تأیید جایگزینی را دوباره می‌گیرد. قبل از شروع، revision تنظیمات انتخاب‌شده، نود، جفت HTTPS و پایان اعتبار دوباره بررسی می‌شوند. تغییر پورت، پروتکل، SNI/مسیر TLS و دیگر settings، خاموشی/حذف ورودی یا نود و تغییر host جفت، شروع نقشهٔ قبلی را متوقف می‌کند. کاربر/دستگاه/حجم در این snapshot نیستند؛ آنها همچنان از عامل و حسابداری عادی مدیریت می‌شوند.

این guard تصمیم شروع را روی DB پنل محافظت می‌کند؛ تغییر فایل گواهی یا تنظیمات روی سرور خارج را از دور تشخیص نمی‌دهد، و تنظیمات را پس از شروع job قفل نمی‌کند. اگر بعداً ورودی را تغییر بدهی، `source_matches=false` نمایش داده می‌شود؛ نصب جاری خودکار rollback نمی‌شود.

claim شروع پیش از درخواست worker در DB commit می‌شود و قفل DB هنگام تماس شبکه باز نمی‌ماند. درخواست هم‌زمان برای همان نقشه دوبار شروع نمی‌شود. timeout به `start_unknown` تبدیل می‌شود؛ دریافت وضعیت بعدی، رسید worker را فقط با plan ID و job ID متناظر تطبیق می‌دهد. اگر رسید پیدا نشود، وضعیت نامطمئن می‌ماند؛ نبود رسید اثبات عدم اجرا نیست و retry خودکار انجام نمی‌شود. worker فقط ۲۰ job اخیر را می‌دهد؛ رسید قدیمیِ حذف‌شده نیازمند بررسی اپراتور است.

نتیجهٔ `succeeded` تاریخچهٔ عملیات نصب حامل است، نه سلامت جاری مسیر یا انتقال VPN. API صریحاً `application_verified=false` و `endpoint_published=false` می‌دهد. تاریخچه با حذف نود پاک نمی‌شود؛ حداکثر ۱۰۰۰ رکورد نگه‌داری و ۱۰۰ مورد اخیر فهرست می‌شود. retention/پاک‌سازی و پذیرش کامل مسیر مرحلهٔ بعد است.

API مالک: `POST /api/tunnels/bindings`، `GET /api/tunnels/bindings`، `GET /api/tunnels/bindings/{id}` و `POST /api/tunnels/bindings/{id}/start` با `confirm_replace=true`. شروع یک plan متصل از endpoint دستی `/start` رد می‌شود تا guard دور زده نشود. endpoint `/state` وضعیت bindingها را نیز با رسیدهای worker تطبیق می‌دهد. ورودی target port/آدرس دلخواه در حالت متصل پذیرفته نمی‌شود.

## پیش‌نیاز و فعال‌سازی

Donino Tunnel با نقش ایران باید **روی همان میزبان کنترل‌پنل** و با نقش خارج روی میزبان مقصد نصب باشد. نسخهٔ قرارداد بررسی‌شده ۰.۴.۰، commit `4c19214598d32bd2868f9f46030d8a5dbd494d97` است. نصب/ارتقای هر دو طرف را طبق [راهنمای همان نسخه](https://github.com/danialrad04-sketch/donino-tunnel/blob/4c19214598d32bd2868f9f46030d8a5dbd494d97/docs/role-setup.md) انجام بده؛ صرف نصب بستهٔ Python جای سرویس‌های نقش و کنترل‌کننده را نمی‌گیرد. مسیر backend مستقل VPN آن پروژه را برای کاربران این پنل نصب نکن؛ Xray و کاربران متعلق به Donino Panel هستند.

در حالت پیش‌فرض اتصال خاموش است. بعد از نصب نقش‌ها، گروه `donino-link` و socket روت ` /run/donino-control/control.sock` باید وجود داشته باشند. برای نصب native پنل، در checkout همین نسخه:

```sh
getent group donino-link
sudo systemctl status donino-control.service
sudo install -d -m 0755 /etc/systemd/system/donino-panel.service.d
# اگر فایل مقصد از قبل وجود دارد، ابتدا محتوای آن را بررسی کن.
sudo install -m 0644 deploy/donino-panel-tunnel.conf /etc/systemd/system/donino-panel.service.d/tunnel.conf
sudo systemctl daemon-reload
sudo systemctl restart donino-panel.service
```

drop-in دسترسی گروهی worker و `DONINO_TUNNEL_BRIDGE=1` را فقط به سرویس پنل اضافه می‌کند. این متغیر را در `/etc/donino/panel.env` روی مقدار مخالف قرار نده؛ `EnvironmentFile` در systemd می‌تواند `Environment` را override کند. worker روت باقی می‌ماند و پنل با کاربر محدود اجرا می‌شود. عضویت این سرویس در گروه کنترل‌کننده یک مجوز قدرتمند محلی است؛ آن را به سرویس‌های نامرتبط نده. حالت کانتینری/worker دوردست در این نسخه پشتیبانی نشده است.

## کار با صفحه

۱. در پنل خارج کد یک‌بارمصرف بساز. در Donino Panel، نام اتصال، IP/دامنهٔ خارج، پورت agent و کد را وارد کن. رمز root یا کلید خصوصی لازم نیست. کد در پاسخ API، audit یا دیتابیس این پنل ذخیره نمی‌شود؛ worker توکن peer را در پوشهٔ خصوصی خودش نگه می‌دارد. پورت مدیریت، پیش‌فرض TCP 9444، باید از ایران به خارج باز باشد. تغییر IP مبدأ/NAT ممکن است به جفت‌سازی دوباره نیاز داشته باشد.

۲. ارتباط مدیریت را آزمایش کن. آماده‌بودن systemd و یکسان‌بودن runtime دو طرف با سلامت انتقال VPN یکسان نیستند. اگر نسخه‌ها متفاوت‌اند، ابتدا هر دو نقش را به نسخهٔ یکسان ارتقا بده.

۳. آدرس ایران و سرویس‌ها را وارد کن. هر سطر `نام,پورت ایران,پورت خارج` است؛ مثال `vpn,443,8443`. مقصد عمداً فقط `127.0.0.1:8443` روی همان خارج است؛ URL، مسیر فایل، دستور shell و IP مقصد دلخواه پذیرفته نمی‌شود. inbound واقعی Xray و گواهی آن باید از قبل روی خارج وجود داشته باشند. شمارهٔ پورت خارجی را با آن inbound تطبیق بده. پورت عمومی روی ایران bind می‌شود؛ از پورت اشغال‌شدهٔ HTTPS همین پنل استفاده نکن.

۴. FRP WSS یا FRP QUIC یا هر دو را انتخاب کن. در این قرارداد فقط سرویس TCP عرضه می‌شود؛ QUIC حامل UDP است و به معنی فوروارد UDP برنامه نیست. شش حامل آزمایشی دیگر Donino Tunnel هنوز از این صفحه عرضه نمی‌شوند. طرح و پورت‌ها را مرور و فایروال میزبان/provider را بررسی کن؛ این اتصال `open_ufw=false` دارد و فایروال را تغییر نمی‌دهد.

۵. تأیید جایگزینی و شروع: **کل مجموعهٔ تانل‌های مدیریت‌شدهٔ دو نقش** جایگزین می‌شود، نه فقط یک سطر؛ مسیرهای قبلی موردنیاز را در نقشه نگه دار. plan یک ساعت اعتبار دارد و یک بار قابل مصرف است. worker آماده‌سازی دو طرف، فعال‌سازی، probe و rollback محافظت‌شده را انجام می‌دهد. بستن صفحه job را متوقف نمی‌کند. در timeout نتیجه نامطمئن است؛ ابتدا وضعیت job را ببین و درخواست شروع/جفت‌سازی را کورکورانه تکرار نکن. audit پنل و journal worker یک تراکنش مشترک نیستند؛ job مرجع اجرای نصب است.

## مرز مدیریت و تضمین

اشتراک‌ها و `nodes.host` خودکار تغییر نمی‌کنند؛ binding پایدارِ ساخت و شروع plan به inbound پیاده شده، اما تأیید انتقال برنامه و انتشار endpoint هنوز اجرا نشده است. تغییر endpoint بدون بررسی SNI/گواهی و آزمون واقعی می‌تواند اتصال کاربران را خراب کند. حجم/انقضا/دستگاه را Xray و عامل Donino Panel روی خارج محاسبه می‌کنند؛ بایت carrier به مصرف کاربر اضافه نمی‌شود. حساب‌های staging شدهٔ doctor-dns با ساخت تانل فعال نمی‌شوند؛ relay گیمینگ همچنان جداگانه لازم است.

مسیر جایگزین مربوط به اتصال‌های **جدید** است؛ بقای نشست TCP قطع‌شده، رفع همهٔ اختلال‌های ایران، سرعت/پینگ یا عبور از همهٔ ISPها تضمین نشده است. قطع کامل کانال مدیریت می‌تواند بازگشت خارج را نامطمئن کند؛ `rollback_failed` نیازمند بررسی واقعی است. خاموش‌کردن bridge فقط دسترسی API پنل را می‌بندد و job جاری یا تانل نصب‌شده را متوقف نمی‌کند.

## قرارداد و آزمون

API فقط برای owner با scope کامل: `GET /api/tunnels/state` و `POST /api/tunnels/{pair,connection,preview,start}`. ورودی‌ها extra-field ممنوع، socket ثابت Unix با مالک root و بدون مجوز world، بدون redirect/proxy محیطی، خروجی با whitelist و سقف ۲ MiB هستند. هیچ endpoint نصب backend VPN، اجرای shell، فایل دلخواه یا URL دلخواه worker از پنل باز نشده است.

`tests/test_tunnel_bridge.py` مرز نقش، opt-in، validation، redaction، socket و عدم retry خودکار را بررسی می‌کند. `tests/test_tunnel_contract.py` با checkout پین‌شده، **worker واقعی روی Unix socket** و renderer/گواهی واقعی، طرح خصوصی دو نقش را می‌سازد و قرارداد پاسخ را بررسی می‌کند. اسکن سرویس میزبان در این fixture جایگزین است؛ این آزمون نصب دو VPS، عبور ترافیک carrier یا شبکهٔ ایران نیست. job جداگانهٔ `tunnel-contract` در CI مانع وابستگی به سورس شناور main می‌شود.

مراحل بعد: نصب عامل دوردست پنل، پذیرش واقعی برنامه و انتشار endpoint فقط پس از تأیید مسیر و revision، مدیریت چند جفت، آزمون واقعی انتقال VPN و شکست/بازیابی روی دو node، جداسازی دسترسی حداقلی worker و سپس حامل‌های بیشتر.
