# Smart DNS و مسیریابی خروجی — alpha 11

این قابلیت برای دامنه‌های انتخابی، HTTPS را از یک خروجی دیگر عبور می‌دهد. پاسخ A/AAAA به gateway دونینو اشاره می‌کند؛ gateway از SNI آشکار دامنه، حسابِ مالک IP و سیاست او استفاده می‌کند و به خروجی اصلی یا جایگزین TLS احرازشده وصل می‌شود. خروجی فقط مقصد عمومیِ مجاز روی TCP/443 را می‌پذیرد. TLS مشتری تا سرویس مقصد دست‌نخورده می‌ماند؛ گواهی مقصد را همان کلاینت بررسی می‌کند.

این برش، زیرساخت عبور HTTPS برای سرویس‌های محدودشده است. موفقیت هر بازی، فروشگاه یا رفع محدودیت جغرافیایی به مقصد، IP خروجی و شبکهٔ کاربر بستگی دارد و در اینترنت واقعی تأیید نشده است. UDP بازی، HTTP ساده، QUIC/HTTP3، DoQ و ECH پشتیبانی این مسیر نیستند. درخواست HTTPS/SVCB دامنهٔ route پاسخ NODATA می‌گیرد؛ ECH موجود در ClientHello رد می‌شود. ابزارهایی که SNI نمی‌فرستند یا از IP ثابت استفاده می‌کنند از این مسیر عبور نمی‌کنند.

## نصب اختیاری روی میزبان پنل

در Debian 12 یا Ubuntu 24.04، با سورس انتشارِ بررسی‌شده و دامنه‌ای که A/AAAA آن درست تنظیم شده است:

```sh
sudo ./install.sh --domain panel.example.com \
  --with-dns --dns-listen 0.0.0.0 --dns-port 53 --dot-port 853 \
  --with-smart-dns --smart-dns-ip SERVER_PUBLIC_IPV4
```

نام دامنه و IP نمونه را جایگزین کنید؛ برای IPv6، `--smart-dns-ip` را دوباره بدهید و از دسترسی واقعی IPv6 مطمئن شوید. `plan` همین گزینه‌ها را برای بررسی اولیه می‌پذیرد. گواهی پنل با مسیر معمول HTTP-01/Certbot گرفته و تمدید می‌شود؛ fixtureها فقط CA محلی را آزموده‌اند، صدور عمومی ACME نیازمند دامنه/VPS واقعی است. DNS ورودی و سرویس‌های دیگر نباید پورت‌ها را اشغال کرده باشند. نصب به‌صورت خودکار firewall میزبان یا ارائه‌دهنده را باز نمی‌کند.

NGINX با ماژول stream، پورت عمومی ۴۴۳ را به اشتراک می‌گذارد: SNI دامنهٔ پنل و اتصال بدون SNI به HTTPS داخلی `127.0.0.1:8443` می‌روند؛ SNIهای دیگر به Smart gateway در `127.0.0.1:8444` می‌روند. گواهی و mTLS پنل همچنان در backend اصلی بررسی می‌شوند. IP واقعی با PROXY v1 فقط از frontend محلی منتقل می‌شود. هیچ‌یک از این دو پورت داخلی را به شبکهٔ عمومی منتقل نکنید. دامنهٔ پنل برای مدیریت رزرو شده است.

طرح NGINX باید include بستهٔ استاندارد `/etc/nginx/modules-enabled/*.conf` را داشته باشد. stream یا listener 443 ناشناخته و فایل managed تغییرکرده تصاحب نمی‌شود؛ پیش از فعال‌سازی سرویس‌ها خطا می‌دهد. شکست آزمون NGINX هر دو فایل frontend و پنل را برمی‌گرداند. فایل global NGINX بازنویسی نمی‌شود. تنظیم اختیاری در نصب مجدد حفظ می‌شود؛ تغییر IPهای تبلیغ‌شده را صریحاً با گزینه‌های جدید بدهید. `repair` سرویس را بازسازی می‌کند و `uninstall` فایل‌ها/سرویس‌های managed را حذف و داده‌ها را نگه می‌دارد.

برای بررسی نقش‌ها:

```sh
sudo ./install.sh doctor
sudo systemctl status donino-smart-gateway donino-dns donino-unbound nginx
```

داشتن frontend به‌تنهایی دسترسی ایجاد نمی‌کند؛ خروجی و حساب زیر هم باید آماده باشند.

## آماده‌سازی خروجی

خروجی نقش جداگانهٔ `agent.smart_exit` است. آن را روی سرور خروجیِ تحت اختیار خود با Python محیط Donino، کاربر سرویس مستقل و گواهی TLS معتبر برای دامنهٔ خروجی اجرا کنید. نصب/تمدید خودکار گواهی این نقشِ دوردست و توزیع تنظیمات آن هنوز پیاده نشده است. نسخهٔ پنل، کاربر سرویس و مسیرهای template را پیش از اجرا تطبیق دهید.

```sh
umask 077
/opt/donino-panel/current/.venv/bin/python -m agent.smart_exit init \
  /etc/donino/smart-exit.json --listen 0.0.0.0 --port 9445 \
  --tls-cert /absolute/path/fullchain.pem --tls-key /absolute/path/privkey.pem \
  --domain service.example.com --domain another-service.example.net
```

این دستور فایل تازهٔ خصوصی 0600 می‌سازد؛ username/password جدید را فقط یک بار برای ثبت در پنل می‌دهد. خروجی دستور را در log عمومی یا گفتگو منتشر نکنید. فایل تنظیم فقط hash رمز را دارد؛ رمز اصلی را برای gateway خصوصی نگه دارید. فایل و کلید TLS باید برای کاربر سرویس خواندنی باشند. هیچ credential، private key یا فایل تنظیم خصوصی را commit نکنید. نمونهٔ [سرویس خروجی](../deploy/donino-smart-exit.service.example) را با مسیرها و کاربر واقعی تنظیم کنید. اجرای مستقیم برای بررسی نقش:

```sh
/opt/donino-panel/current/.venv/bin/python -m agent.smart_exit run /etc/donino/smart-exit.json
```

دامنه‌های مجاز و زیردامنه‌های آن‌ها پذیرفته می‌شوند. برای کاتالوگ، suffixهای انتخاب‌شده در سیاست را در allowlist خروجی هم قرار دهید؛ انتخاب گروه در پنل، فایل خروجی دوردست را خودکار تغییر نمی‌دهد. خروجی، نام را یک بار resolve و همهٔ جواب‌ها را بررسی می‌کند: private/loopback/link-local و IPv6 انتقالی/نگاشت‌شده رد می‌شوند؛ اتصال به IP عمومی بررسی‌شده است. مقصد IP مستقیم و پورت غیر از ۴۴۳ پذیرفته نمی‌شود. پورت TLS خروجی را فقط برای gatewayهای موردنیاز در سیاست شبکهٔ خود در دسترس قرار دهید.

## تنظیم از پنل

۱. در بخش DNS، «نود خروجی جدید» را با host/port، نام گواهی TLS و credential خصوصی بسازید. ابتدا غیرفعال ذخیره کنید. «آزمون اتصال خروجی» باید TLS و احراز هویت را موفق ببیند؛ سپس حالت را فعال کنید. این آزمون به معنی موفقیت سرویس مقصد نیست. در حالت عادی trust store سیستم استفاده می‌شود؛ CA خصوصی را فقط با فایل مورداعتماد و `DONINO_SMART_DNS_CA` مشترک در محیط پنل و gateway تعریف کنید.

۲. با «مسیریابی دامنه» خروجی اصلی و حداکثر دو جایگزین متفاوت انتخاب کنید. انتخاب «مسیریابی از کاتالوگ» قواعد سرویس‌ها را می‌سازد؛ سیاست را به حساب DNS کاربر اختصاص دهید. `allow` استثنای resolver مستقیم و `block` مسدودسازی است. دقیق‌ترین suffix اولویت دارد. ساختار دستی:

```text
route example.com UUID_PRIMARY,UUID_FALLBACK
allow direct.example.com
block blocked.example.com
```

۳. در «مجوز و حجم relay»، Smart DNS را برای حساب فعال، حجم مستقل و سقف اتصال را تعیین کنید. صفر حجم یعنی نامحدود؛ این مجوز پیش‌فرض غیرفعال است. enabled و تاریخ انقضای کاربرِ والد نیز اعمال می‌شوند.

۴. کاربر از پورتال خودش IP فعلی را ثبت کند. اثبات IP همان سازوکار HTTPS پنل است؛ header دلخواه یا صرفِ توکن DoH مالکیت IP ایجاد نمی‌کند. DNS درخواست‌شده و اتصال HTTPS باید از IP ثبت‌شدهٔ همان حساب برسند. CGNAT، VPN دیگر یا تفاوت خروجی IPv4/IPv6 می‌تواند تعارض ایجاد کند. DNS کلاینت را به gateway تنظیم و سرویس موردنظر را جداگانه آزمایش کنید. resolver عمومی واسط معمولاً IP کاربر را به این gateway نمی‌رساند و جای DNS مستقیمِ حساب را نمی‌گیرد.

## تعویض نود و حسابداری

جایگزین فقط پیش از ارسال TLS مشتری انتخاب می‌شود. قطع همهٔ خروجی‌ها باعث رد اتصال است؛ DIRECT fallback خودکار وجود ندارد. اولویت را تغییر دهید تا اتصال‌های تازه از نود بعدی بروند. نشست جاری روی مسیر دیگر replay نمی‌شود. تغییر سیاست می‌تواند نشست‌های جاری آن سیاست را ببندد. حالت «تخلیه» اتصال تازه به آن نود را متوقف می‌کند و اتصال‌های مجاز جاری را نگه می‌دارد؛ «غیرفعال» آن‌ها را نیز می‌بندد. تغییر host/port/SNI/credential، ذخیرهٔ غیرفعال و آزمون تازه می‌خواهد.

حجم relay مجموع بایت‌های TLS مشتری در دو جهت است که gateway پیش از write اتمیک رزرو می‌کند. بایتِ رزروشده در write ناموفق ممکن است شمرده شود؛ این عدد حجم سیمِ ارائه‌دهنده، UDP بازی، بایت درخواست DNS یا مصرف VPN نیست. کنترل حجم پیش از هر قطعه و کنترل مجوز در نگهبان تقریباً یک‌ثانیه‌ای انجام می‌شود. دفتر دورهٔ نشست ثابت است؛ ریست دوره، نشست قدیمی را به دورهٔ تازه منتقل نمی‌کند. مجوز IP، انقضا، غیرفعال‌سازی، تغییر revision و قطع DB جریان را می‌بندند. خاموشی gateway بعد از lease ده‌ثانیه‌ای پاسخ route تازه را SERVFAIL می‌کند؛ TTL پاسخ قبلی ۳۰ ثانیه است.

## حدود انتشار و گام‌های v1

schema 13 پیش از مهاجرت backup می‌گیرد. restore تاریخچه را نگه می‌دارد اما خروجی‌ها و مجوز relay حساب‌ها را خاموش و نشست‌های باز را می‌بندد؛ پس از بازیابی، گواهی/credential/شبکه را دوباره آزمون و مجوزها را آگاهانه فعال کنید. واردات doctor-dns همچنان staged است؛ حجم قدیمی و حساب غیرفعال آن خودکار به حجم/مجوز جدید تبدیل نمی‌شود.

پذیرش loopback شامل DNS واقعی، HTTPS با گواهی معتبر، دو خروجی، تغییر سیاست، قطع خروجی، TLS/auth نامعتبر، حجم و ابطال است. resolver/dial آزمایشی فقط در fixture شبکه مقصد loopback را مجاز می‌کند؛ کد خروجی تولید چنین گزینه‌ای ندارد. ذخیره‌سازی با writer lock موجود کار می‌کند و هر قطعه transaction دارد؛ ظرفیت و throughput بالا هنوز اندازه‌گیری نشده‌اند. حد پیش‌نمایش: ۱۰۰ خروجی، ۱۲۸ handler gateway، سقف DB برابر ۲۵۶ نشست فعال، ۱ تا ۶۴ اتصال هر حساب و حداکثر ۱۰۰ هزار رکورد تاریخچه؛ retention خودکار این تاریخچه هنوز آماده نیست. idle برابر ۹۰ ثانیه و حداکثر عمر اتصال یک روز است؛ half-close عمومی TCP تضمین نمی‌شود.

برای v1 هنوز نصب و چرخش گواهی/اعتبارنامهٔ نقش دوردست، DNS چندنودی، ظرفیت/retention، آزمون واقعی بازی و اینترنت، تکمیل WireGuard/OpenVPN و gateهای [طرح جامع](MASTER-PLAN.fa.md) باقی‌اند. alpha 11 پیش‌نمایش قابل‌آزمون است؛ ادعای پشتیبانی همهٔ پروتکل‌ها یا v1 پایدار ندارد.
